Abstract — New capabilities to compute adjoint-weighted kinetics parameters have been developed,
tested, validated, and made available in OpenMC, an open-source Monte Carlo particle transport
code. The effective delayed neutron fraction βeff and the effective generation time Λeff are calculated
using the iterated fission probability (IFP) method. Effective kinetics parameters produced with
OpenMC are compared to a prior work performed with a developmental branch of OpenMC and
other results from Serpent and MCNP based on several benchmark cases from the ICSBEP
(International Criticality Safety Benchmark Evaluation Project). Overall, the results are in good
agreement with a maximum difference in βeff of 25 pcm and 2.7% for Λeff .
The results of the new IFP implementation are also compared to design data used in theoretical kinetics
models for the ARE (Aircraft Reactor Experiment) and the Molten Salt Reactor Experiment (MSRE) when
the fuel is not circulating. Reasonable agreement was obtained for both experiments with a maximum
difference in βeff of 54 pcm and 13.4% for Λeff .
This new feature is fully compatible with shared- and distributed-memory parallelism. The impact of the
new implementation on code performance was verified to be minimal when IFP was not used with a maximum
relative difference of 0.2% in peak memory usage and 0.8% in execution time for the model considered. When
using the new IFP feature, the code performance scaled with the number of processes and threads, as expected.
Keywords — Kinetics parameters, iterated fission probability, OpenMC.

I. INTRODUCTION
Kinetics parameters play an essential role in the
safe operation of nuclear reactors. Having the capabil­
ity to compute these parameters accurately is impor­
tant to justify the safety of existing nuclear reactors
and for the development of advanced designs.
Effective kinetics parameters for a point reactor are
derived from transport theory by using the forward
and adjoint transport equations [1]. Using the notion
of adjoint flux, the effective delayed neutron fraction
βeff and the effective generation time Λeff can be
defined as [1]:

present in the system at a given time weighted by the adjoint

excess of this value will make a nuclear system reach prompt
criticality. The effective generation time Λeff can be inter­
preted as how long it takes for a neutron to “reproduce itself”
by fission [2].
Eqs. (1) and (2) both use the neutron adjoint flux, which
is not trivially obtained from standard Monte Carlo (MC)
neutron transport simulations. While it is possible to solve
for the adjoint flux directly in multigroup MC neutron
transport by adjusting the fission and scattering terms [3],
this technique is not applicable to continuous-energy MC
neutron transport [4,5]. A common approach used to
approximate the effective kinetics parameters is to rely on
the difference between a reference and a perturbed state of
a system (e.g., the “prompt method” [6] to calculate βeff and
the “1=v absorber method” [7] to calculate Λeff ). The main
drawback of this approach is that it requires two full calcu­
lations of the same system. Another approach that has been
widely adopted among MC neutron transport solvers,
including MCNP [5], Serpent [2], and TRIPOLI [8], is the
iterated fission probability (IFP) method [9]. The founda­
tional idea behind this method is that the number of fission
neutrons descending from an initial neutron at a given phase
space is proportional to the adjoint flux at this phase space
provided that the neutron flux has already converged to its
fundamental mode and that the number of generations Ngen
between the initial neutron and its descendants is suffi­
ciently large [10]. Tracking the population of descendants
of a given neutron is possible in continuous-energy MC
calculations by storing additional data during iterations,
and thus, can be used to evaluate βeff and Λeff. The only
unknown parameter needed to use IFP is the number of
generations Ngen, which must be large enough to converge
the descendant population while limiting the memory bur­
den and avoiding an increase in statistical uncertainty
observed when Ngen is large [8]. Generally, this parameter
is problem dependent and difficult to predict [5]. A number
of generations between 10 and 20 is assumed to be sufficient
for most cases [8]. A specific case of IFP where only the
next generation is considered is known as the next fission
probability (NFP) method. More recent work from Peng
et al. [11] used a developmental branch of OpenMC [12] to
compute adjoint-weighted kinetics parameters from the
CLUTCH (contributon-linked eigenvalue sensitivity/uncer­
tainty estimation via tracklength importance characteriza­
tion) method described in Ref. [3]. This prior work, which
also included an implementation of IFP and NFP, was never
merged into the main branch of OpenMC as it needed
further development to enable its integration.

In this paper, a new implementation of IFP in
OpenMC based on the Serpent approach [2] is pre­
sented. This implementation has been coded from the
ground up and merged to the develop branch of the
main OpenMC repository (commit 47ca2916) via a pull
requesta. The IFP implementation was later corrected
and merged to the develop branch (commit 767db7e6a)
via another pull requestb. The main focus of this work
is to guarantee that the new implementation has mini­
mal impact on performance when IFP is not used and
that using multiple processes when IFP is used still
improves the performance of the code. Several bench­
mark cases from the International Criticality Safety
Benchmark Evaluation Project (ICSBEP) [13] were
used to validate the results of the new IFP implementa­
tion in OpenMC against the results from Serpent and
MCNP reported in Ref. [2] and the results from Peng
et al [11]. Additionally, results from the new imple­
mentation are compared to design data used in theore­
tical kinetics models for the Aircraft Reactor
Experiment (ARE) and the Molten Salt Reactor
Experiment (MSRE). Particular efforts have been
made to minimize the impact of this IFP implementa­
tion on memory and execution time. A performance
analysis is provided to assess the impact on peak
memory usage and execution time.

II. METHODS
Proportionality between the adjoint flux at a given
location in phase space and the number of descendants in
a future generation from a common ancestor at the same
location can be demonstrated using a balance equation
and proving that the number of descendants is a solution
to the adjoint transport equation [10]. The underlying
assumption of this demonstration is that the neutron
flux in the generation that saw the emission of the com­
mon ancestor has converged to its fundamental mode and
that the number of generations between the ancestor and
the descendants is large enough to see the convergence of
the number of descendants [10]. Given the form of
Eqs. (1) and (2), having access to a quantity that is
proportional to the adjoint flux, namely, the number of
descendants in a future generation under proper condi­
tions, is a sufficient condition to solve for the effective

III. IMPLEMENTATION IN OPENMC
To obtain the effective kinetics parameters as defined
in Eqs. (6) and (7), a record of the precursor group
(setting 0 for prompt neutrons by convention) and life­
time of a given set of ancestors has to be kept for each
neutron transported during the simulation. The number of
consecutive neutron ancestors to consider in the IFP
method is referred to as the number of generations Ngen.
The optimal value of Ngen is model dependent and is
generally found empirically by monitoring the conver­
gence of kinetics parameters for different values of
Ngen. Ngen, therefore, has been added as a user-defined
parameter in the settings of OpenMC. It is considered
constant during the entire simulation, and its default value
is set to 10. Ngen can be set by the user via the Python
application programming interface (API) from the fol­
lowing commands:

Because the number of generation Ngen is deter­
mined at run time, ancestors’ lifetimes and precursor
groups are stored in dynamic data containers (vec­
tors). The memory overhead associated with dynamic
data containers allocated at run time can have
a nonnegligible impact on the total memory footprint,

especially when data containers are present in
a significant number and even if these containers
are empty (i.e., when the IFP feature is not requested
by the user). To ensure the memory impact of the IFP
feature on OpenMC is negligible when it is not
requested, IFP-related data (precursor group numbers
and lifetimes of ancestors) are not stored as particle
attributes, but rather in four global data banks (vec­
tors of vectors). Two of these banks are dedicated to
storing vectors of ancestor precursor group numbers
for every neutron, and the other two contain vectors
of ancestor lifetimes. The power iteration process
used in OpenMC requires two separate banks per
type of data type. One bank (called the source
bank) is used to store the information relative to the
source particles of a given generation, while
the second bank (called the fission bank) holds the
information relative to the fission sites that result
from the transport of particles during this generation
and that will be used as sources in the following
generation. IFP data sets relative to a given source
particle are stored in IFP source banks using the same
index that was used to store the source particle in the
source bank. Similarly, IFP data sets stored in the IFP
fission banks use the same index that was used to
store the fission site in the fission bank. This
approach guarantees that the IFP implementation in
OpenMC is thread-safe and can work with multiple
processes. While using the same data banks for both
data types with structs containing one integer and one
floating point value (for the precursor groups and the
lifetimes, respectively) was initially seen as a more
effective way to transfer memory between processes
during parallel execution, the extra padding added to
the struct for memory alignment was deemed unac­
ceptable. Having two separate data banks also offers
the added benefit of being able to calculate βeff and
Λeff independently.

is sampled, new fission sites are created and stored in the
fission bank. The calculated lifetime of the particle that gen­

IV. RESULTS AND VALIDATION
All calculations performed in this section were run
on a system with a dual-socket Intel Xeon Platinum 8260
processor with 24 physical cores per processor, each of
which had two hardware threads per core for a total of
96 hardware threads. OpenMC was configured to use the
latest commit 767db7e6a (including both pull requests).

IV.A. ICSBEP Benchmarks
Table 1 summarizes the ICSBEP benchmark cases
selected for computational comparison. The results using
Serpent 2.1.15 and MCNP5 v1.60 were obtained from
Ref. [2]. The kinetics parameters produced with OpenMC
were generated for two different nuclear data libraries,
JEFF-3.1.1 [14] and ENDF/B-VII.1 [15], to allow for
direct comparison with the results reported in the
Serpent analysis [2] and in the work from Peng
et al. [11], respectively. Nuclear data based on JEFF3.1.1 were generated in the OpenMC HDF5 format
from the original ENDF files using the openmc.data
module of OpenMC and NJOY 2016.74 [16]. For all
cases in this section, OpenMC was run using 20 000

particles per batch, 2000 active batches, 100 inactive
batches, and to be consistent with the Serpent results
in Ref. [2], 15 generations for IFP.

OpenMC using JEFF-3.1.1 are presented in Tables

V. PERFORMANCE EVALUATION
Performance of the new implementation was eval­
uated by measuring the execution time and memory
usage using the stacy-029 (LEU-SOL-THERM-004)
model, run 29, from the ICSBEP [13]. All calculations
performed in this section were run on the same hard­
ware as in Sec. IV. OpenMC was run using 400 000
particles per batch for 20 inactive plus 10 active
batches and used nuclear data from ENDF/B-VIII.0
[25]. The execution times were obtained by taking the
average time of five consecutive OpenMC runs. This
approach ensured that external factors like job schedul­
ing had a limited impact on the evaluation. Memory
usage was obtained by taking the average of the peak
memory usage from five consecutive OpenMC runs.
Individual memory usage values for OpenMC pro­
cesses were measured every 0.5 ms by taking the pro­
portional set size reported by the psutil Python
package. Peak memory usage values for each process
were obtained by taking the maximum value over all

10

J. DORVILLE ET AL.

time steps. The peak memory usage for a run was then
obtained by summing the peak memory usage values
for every process.

V.A. Impact of the New IFP Implementation
The new IFP implementation introduced data
structures in both the message passing interface
(MPI) and non-MPI parts of the source code. To
ensure that the performance was not impacted regard­
less of whether the executable was compiled with or
without MPI, both configurations were evaluated.
Tables 9 and 10 show a comparison of the perfor­
mance metrics between a reference state and a new
state containing the IFP implementation. The refer­
ence state corresponded to the state of the OpenMC
source code before IFP was implemented (commit
c1a4d43da in the main OpenMC repository). Because
IFP was fully implemented from two pull requests,
OpenMC developments that happened between these
two pull requests should not be taken into account to
allow for a fair comparison with the reference state.
This is why the new state considered here was built

from a custom branch based on the first time the IFP
feature was merged into the develop branch (commit
47ca2916 in the main OpenMC repository) and the
correction (commit 767db7e6a) was applied directly
after. All runs in this section used 24 threads and
a single process. As expected, the implementation
had no significant impact on code performance when
the IFP method was not used.
The impact of using the IFP method was evaluated
by running the model with IFP on and off. The corre­
sponding results are reported in Table 11. Compared to
a reference calculation, using IFP in the same conditions
with the same model for 15 generations significantly
increased both the execution time (42.1%) and memory
usage (45.1%). This result was expected, as IFP ulti­
mately requires storing additional attributes for each par­
ticle simulated (to store the precursor groups and
lifetimes of their ancestors).

VI. CONCLUSIONS
The IFP method has been implemented, tested, and
validated in OpenMC. This new feature allows users to
compute effective kinetics parameters (effective delayed
neutron fraction βeff and effective generation time Λeff )
for their OpenMC model by only adding a new setting
and requesting three new tallies. It provides an easy way
to generate the fundamental parameters needed to per­
form static and transient reactor safety analyses, and only
necessitates one MC calculation as opposed to the two
calculations involved in the perturbation-based approach.
The new feature showed good agreement compared to
computational results based on cases from the ICSBEP
benchmark [13] reported for Serpent [2], MCNP [2], and
a previous developmental branch of OpenMC [11] with

Λeff. Comparisons to design data used in theoretical
kinetics models for MSR experiments (ARE and

a maximum difference in βeff of 54 pcm and 13.4% for
Λeff. The impact of the new implementation on code
performance was verified to be minimal when IFP was
not used with a maximum relative difference of 0.2% in
peak memory usage and 0.8% in execution time for the
